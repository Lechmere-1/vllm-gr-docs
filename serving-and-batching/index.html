    Serving and batching¶

    Start with Online serving and its successful single-prompt request. This page extends that setup to one four-prompt completions request, with fixed Beam width 128 and three generated SID components. Use the same installed accelerator environment, model snapshot, artifact, and repository root.

    A prompt list is different from concurrent requests¶

    Workload HTTP requests Possible V1 execution
    One prompt 1 One single-item session
    Four prompts in one supported list 1 One session with four fixed members
    Four independent simultaneous calls 4 Separate sessions awaiting the execution owner

    The V1 execution contract has one active execution owner and two dispatch slots. Those slots allow stages of that owner to overlap; they do not create two independent active sessions. Members of a batch are fixed before execution. This is not continuous batching or automatic coalescing across HTTP requests.

    beam.online_batch_sizes selects exact prompt-list sizes that the completions route can submit as one session. The schema accepts unique integers in 1..8, requires 1, and normalizes their order. The default is [1, 2, 4]; the initial online guide deliberately uses [1]. Engine capacity, this HTTP policy, and graph captures are separate settings.

    The route claims non-streaming Beam completions with ordinary text or token-ID prompts and a selected size. Other cases retain the original route. A list of three does not become batches of two and one under policy [1, 4]. Declines log Beam batch declined with the reason; they need not be HTTP errors.

    Size the whole execution¶

    For fixed B=4 and width W=128, Decode has B * W = 512 physical token rows. max_num_seqs bounds logical requests: this batch needs at least 4, not 512. The physical Decode rows instead require a max_num_batched_tokens budget of at least 512 on NPU. Admission checks these two capacities separately. The launch command below retains --max-num-seqs 512 as generous headroom, not the minimum for B=4; larger settings can increase startup/resource costs. Neither capacity grants additional active execution owners.

    Prefill has a different budget: sum all four complete input lengths, including the BEGIN token appended to each prompt. Chunked Prefill remains disabled. A 512-token Decode budget is insufficient for four 400-token prompts:

    Decode rows:           4 * 128       = 512
Prefill input tokens:  4 * (400 + 1) = 1604

    Use max_num_batched_tokens >= max(512, total_prepared_prompt_tokens) and allow for any smaller max_num_scheduled_tokens limit. Each prompt plus its effective generation budget must also fit max_model_len. The command below uses model length 512 and total token budget 2048; it is not a sizing rule for longer inputs. KV memory, model restrictions, and admission checks still apply.

    Prepare a four-prompt configuration¶

    Stop the previous server before replacing it. In its accelerator shell, retain MODEL, BACKEND, and WORKDIR from the online or data-preparation guide. For a new shell, restore the actual values, for example:

    export MODEL="$PWD/models/OneRec-1.7B"
export WORKDIR="$PWD/results/data-preparation"
export BACKEND=npu  # Use cuda for the CUDA installation.
export API=http://127.0.0.1:8000
export VLLM_USE_V2_MODEL_RUNNER=0
export VLLM_WORKER_MULTIPROC_METHOD=spawn
test -f "$WORKDIR/vllm_gr_config.yaml"

    If you prepared files under results/online-serving, restore that WORKDIR instead. Write a separate YAML while preserving the artifact identity:

    python - <<'PY'
import os
from pathlib import Path
import yaml
from vllm_gr.config import gr_config_to_mapping, load_gr_config, gr_config_from_mapping

work = Path(os.environ["WORKDIR"]).resolve()
config = load_gr_config(work / "vllm_gr_config.yaml")
table = config.constraint_table
if table is None or not table.enabled or table.backend.value != os.environ["BACKEND"]:
    raise ValueError("Reuse an enabled table for the selected backend")
if config.beam_max_width != 128 or config.beam_max_decode_steps != 3:
    raise ValueError("This example requires capacity 128 and three SID steps")
raw = gr_config_to_mapping(config)
raw["beam"].update(online_batch_sizes=[1, 4], graph_batch_size=4)
gr_config_from_mapping(raw)
path = work / "vllm_gr_batch4.yaml"
path.write_text(yaml.safe_dump(raw, sort_keys=False), encoding="utf-8")
print(path)
PY

    The artifact remains shared configuration, not request data. All members use one Beam parameter set and one effective generation budget. Different prompt lengths are allowed if all budgets and model limits fit; the route does not silently shorten one request to match another. This example keeps the guide's CUDA graph setting and NPU eager setting.

    Start the replacement server in the foreground:

    device_args=()
if [ "$BACKEND" = npu ]; then
  device_args=(--block-size 128 --enforce-eager)
elif [ "$BACKEND" != cuda ]; then
  echo 'BACKEND must be cuda or npu' >&2
  exit 1
fi
vllm-gr serve "$MODEL" \
  --host 127.0.0.1 --port 8000 \
  --served-model-name onerec --trust-remote-code \
  --vllm-gr-config "$WORKDIR/vllm_gr_batch4.yaml" \
  --max-model-len 512 --max-num-batched-tokens 2048 \
  --max-num-seqs 512 --max-logprobs 128 \
  --gpu-memory-utilization 0.5 \
  --async-scheduling --no-enable-chunked-prefill \
  "${device_args[@]}"

    This keeps TP/PP/DP/DCP/PCP at 1. The current V1 runtime requires a uniform text decoder, FP16/BF16, and no LoRA, quantization, speculative decoding, multimodal inputs, or KV transfer. Raising batch capacity does not add those capabilities.

    Check readiness and send one request¶

    In a second terminal on the same host, activate the matching environment and restore MODEL and WORKDIR above, then run:

    export API=http://127.0.0.1:8000
curl --fail --silent --show-error --max-time 5 "$API/health"
curl --fail --silent --show-error --max-time 5 "$API/v1/models" | python -m json.tool

    Wait for HTTP 200 and the alias onerec. These checks establish service/engine availability, not that a B=4 request or its graph will succeed. Use the request below as the functional readiness check for this shape.

    Generate valid JSON with four token-ID prompts. This makes the input IDs explicit and lets the response checker attribute choices even when fewer than 128 candidates survive. The same endpoint also accepts a list of text prompts.

    python - <<'PY'
import json
import os
from pathlib import Path
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained(os.environ["MODEL"], trust_remote_code=True)
texts = [
    f"User {i}. Video history: <|sid_begin|><s_a_346><s_b_6566><s_c_5603><|sid_end|>.\n"
    "Recommend the next video."
    for i in range(4)
]
prompts = [tokenizer.encode(text, add_special_tokens=False) for text in texts]
if any(not ids or len(ids) + 5 > 512 for ids in prompts):
    raise ValueError("Each input must fit the conservative public token budget")
if len({tuple(ids) for ids in prompts}) != 4:
    raise ValueError("Use four distinct prompts for this response-attribution example")
if sum(len(ids) + 1 for ids in prompts) > 2048:
    raise ValueError("Combined Prefill exceeds the server's token budget")
request = {
    "model": "onerec", "prompt": prompts,
    "use_beam_search": True, "stream": False,
    "n": 128, "temperature": 0.0, "max_tokens": 5,
    "ignore_eos": True, "skip_special_tokens": False,
    "include_stop_str_in_output": True, "return_token_ids": True,
    "vllm_xargs": {"begin_token": "<|sid_begin|>", "end_token": "<|sid_end|>"},
}
path = Path(os.environ["WORKDIR"]) / "batch4-request.json"
path.write_text(json.dumps(request, indent=2), encoding="utf-8")
print("prepared_prefill_tokens=", sum(len(ids) + 1 for ids in prompts))
print(path)
PY

curl --fail-with-body --silent --show-error \
  --connect-timeout 5 --max-time 120 \
  "$API/v1/completions" -H 'Content-Type: application/json' \
  --data-binary "@$WORKDIR/batch4-request.json" \
  --output "$WORKDIR/batch4-response.json" \
  --write-out 'HTTP batch elapsed: %{time_total}s\n'

    n is the per-prompt Beam width, not batch size. max_tokens=5 reserves the two markers and searches three SID components. The online V1 entry enforces ignore_eos=True. return_token_ids requests output IDs and accepted prompt IDs; this example does not request per-token log probabilities or chat templates. Constraint artifact paths and digests belong to server YAML, not this payload. See parameters for dynamic widths and platform limits. A prompt list does not enable NPU per_parent_beam_widths or per-prompt Multi-Trie selection in this snapshot. Those candidate/constraint capabilities must be checked separately from the number of prompts.

    Interpret choices and actual batching¶

    The non-streaming response flattens prompt-major outputs and numbers index continuously. When every prompt returns 128 results, divmod(index, 128) gives the input position and rank. If fewer results survive, that shortcut is wrong. Use the requested prompt IDs for this example instead:

    python - <<'PY'
import json
import os
from pathlib import Path

work = Path(os.environ["WORKDIR"])
request = json.loads((work / "batch4-request.json").read_text())
response = json.loads((work / "batch4-response.json").read_text())
if "error" in response:
    raise SystemExit(response["error"])
owners = {tuple(ids): i for i, ids in enumerate(request["prompt"])}
counts = [0] * 4
for choice in response["choices"]:
    owner = owners[tuple(choice["prompt_token_ids"])]
    rank = counts[owner]
    counts[owner] += 1
    if rank == 0:
        print(owner, choice["index"], choice["token_ids"], choice["finish_reason"])
print("returned_per_prompt=", counts)
print("usage=", response.get("usage"))
PY

    usage.prompt_tokens sums accepted original inputs; completion accounting sums the returned tails, including configured output boundaries. A legal SID does not establish recommendation quality. Compare quality for the deployed batch shape; B=1 and B=4 are not guaranteed to have identical numerical rankings.

    The response shape alone cannot establish one B=4 session. Check server logs for Beam batch session ... prompts=4 and any Beam batch declined reason. Resource shortages can queue or reject work even after frontend checks pass.

    NPU graphs, timing, and shutdown¶

    NPU Beam FULL replay needs the exact captured (logical batch, input width): (4, 128) differs from both (1, 128) and another factorization of 512 rows. To try it, enable beam.graph_enabled, retain graph_batch_size: 4, remove --enforce-eager, and restart. Dynamic schedules also need matching Decode input-width captures. Prefill capture has separate controls. CUDA ModelRunner V1 uses its own startup capture policy; this YAML does not guarantee B=4 replay.

    NPU capture also requires the supported pure Beam/xllm path, persistent buffers, and request-ordered contiguous pool slots starting at 0. Pool slots identify members' KV storage, not independent execution owners. Internal _beam_graph_full_dispatch_count counts FULL dispatch selections; _beam_graph_fallback_count and its reason map count misses, not necessarily whole-forward eager execution. These are Worker diagnostics, not public HTTP fields. Use the validation guide for actual evidence.

    The curl time includes queueing, HTTP, preprocessing, execution, and response construction for the whole list. Dividing by four does not measure an individual request's latency. For repeated steady-state runs, report batch latency and prompt throughput separately, with warmup, graph/cache state, and inputs fixed.

    A client timeout closes its wait; it does not prove device work has drained. The claimed list route closes its generator on cancellation, and the async session client retains abort/release cleanup ownership. Do not assume every network disconnect, delegated route, or immediate retry has completed cleanup. Record the error and server logs before retrying instead of launching duplicate work automatically. To stop the foreground server you started, press Ctrl+C in that terminal and wait for shutdown. Avoid killing unrelated accelerator jobs.
