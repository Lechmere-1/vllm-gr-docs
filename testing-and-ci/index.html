    Testing and CI¶

    Select validation from the behavior being changed, using the installed runtime for that platform. Read Developer guide for code ownership and Validation and benchmarking for comparing inference results. Commands below belong to the inference repository root.

    Choose the right evidence¶

    Level What it establishes Main prerequisites
    Documentation checks Formatting, characters, spelling, links, and command consistency Selected hooks; no accelerator
    Host/contract regression Configuration, routing, ownership, or isolated function behavior The test's actual dependencies and fixtures
    Kernel/integration tests Numerical and layout behavior of selected device paths Matching CUDA or Ascend runtime and allocated device
    Model/system tests End-to-end public API, lifecycle, numerical output, or graph behavior Model snapshot, artifact, runtime, device, and test data
    Benchmark acceptance Results against the resolved accuracy/performance policy Fixed dataset, input identity, baseline, and saved evidence
    Wheel smoke Installation metadata and import behavior outside the checkout Build tools and packaging dependencies

    A host-oriented test can require Torch and vLLM through tests/conftest.py, even when it never accesses a device. A CPU wheel or reference selector does not establish a production CPU Beam inference runtime. Inspect collection, fixtures, availability guards, and model requirements before choosing a command.

    Each test needs its registered tier: cpu_test, gpu_test, or npu_test. model_test is an additional requirement, not a replacement for a platform tier. Missing tier declarations can fail collection. Markers do not themselves skip tests; selection expressions and availability guards have separate roles. Follow the test-tier rules for mixed modules instead of using a broad not cpu_test filter that drops device cases within CPU modules.

    Start with targeted checks¶

    For a configuration change, inspect and run the owning regression file:

    python -m pytest -q tests/test_gr_config_v1.py

    For selected kernel/integration behavior, use the respective prepared runtime and replace device 0 with the device allocated to your run:

    CUDA_VISIBLE_DEVICES=0 python -m pytest -q tests/kernels/test_rec_constrained_topk_cuda.py
ASCEND_RT_VISIBLE_DEVICES=0 python -m pytest -q tests/constraints/test_npu_backend_integration.py

    For OneRec-1.7B system coverage, set VLLM_GR_TEST_MODEL to the local directory containing configuration, tokenizer, and weights. For example, in Ascend:

    VLLM_GR_TEST_MODEL=/absolute/path/to/OneRec-1.7B \
HF_HUB_OFFLINE=1 ASCEND_RT_VISIBLE_DEVICES=0 \
python -m pytest --run-slow -q tests/st/test_onerec_v1_npu_e2e.py

    That suite needs the Ascend stack and xllm Beam operators. Its own shape/bucket contract determines coverage; success is not evidence for every padding shape. CUDA's corresponding scheduling entry is tests/st/test_onerec_v1_scheduler_st.py. Missing prerequisites can cause skips or failures. HF_HUB_OFFLINE=1 prevents model-hub fallback downloads, not every possible setup operation. Report the actual selected/passed/skipped cases.

    Check documentation without launching the full suite¶

    Use explicit hook IDs on the complete changed file list. Replace the example path below with the real Markdown paths:

    pre-commit run markdownlint --files docs/development.md
pre-commit run check-characters --files docs/development.md
pre-commit run typos --files docs/development.md
pre-commit run end-of-file-fixer --files docs/development.md
pre-commit run trailing-whitespace --files docs/development.md
pre-commit run mixed-line-ending --files docs/development.md
git diff --check

    Also inspect new untracked files, relative links, commands, and generated-site navigation. A strict site build is useful when changing site configuration; Markdown lint alone does not establish that a command works or a page resolves.

    pre-commit run --all-files includes the full slow pytest suite. Even pre-commit run --files ... can invoke the run-tests hook, whose pass_filenames: false does not narrow pytest to those files. Do not substitute either command for the documentation-only hooks above.

    Understand inference-repository CI¶

    For PRs into main or decode_graph, full validation requires a non-draft PR and the ready label. Pushing while it remains, adding it, or marking a labeled draft ready can start validation. Removing it or converting to draft cancels the old PR run and skips new validation. Wheel builds have their own path filters.

    abtest requests a separate performance A/B path for eligible non-draft PRs; its success alone does not satisfy the full gate. Confirmed documentation-only PRs do not run A/B, even with that label. Other label changes are not a general request to run full CI. Review events can also trigger this workflow; a newer run can cancel the previous run for the same PR. Inspect the current head.

    The narrow docs-only classifier covers Markdown under docs/ and designated root Markdown files (README.md, CONTRIBUTING.md, AGENTS.md, CLAUDE.md). It still requires the applicable non-draft/label conditions. Site YAML, SVG, requirements, mixed changes, or uncertain classification are not automatically eligible just because their purpose is documentation. The target branch must already contain the classifier; independent Jenkins jobs have separate rules.

    The required Benchmark blocking gate checks the relevant documentation/full jobs and rejects failed, cancelled, or skipped blocking results. A queued job has no passing result yet; inspect runner assignment and logs before blaming the change. See Contributing and the pinned workflow.

    Preserve accuracy and performance boundaries¶

    Legal SIDs and passing device tests do not establish Recall. Compare tokens, scores, rankings, and model/dataset metrics according to the declared contract. Graph flags are not replay evidence, and an eager/graph comparison is different from a cross-version performance comparison. Keep numerical and latency results separate, with identical inputs and recorded graph/cache/warmup settings.

    Acceptance policy is resolved by target branch, device, and baseline provenance. Do not relax thresholds, replace failures with skips, or select a new dataset to make a gate pass. Record code/import origin, runtime, device, model/tokenizer, artifact, command, baseline/candidate identity, and output files. Historical measurements only support their recorded configuration; a Jenkins success does not automatically update GitHub Actions or validate a different PR revision.

    These CI rules belong to the inference repository. The separate website publication repository has its own deployment checks and permissions; publishing generated pages neither runs accelerator CI nor grants access to their source.
