    Python integration¶

    Embed one constrained OneRec Beam request in a Python application without starting an HTTP server. This example reuses a persistent artifact and canonical YAML from Online serving or Data and constraints. It uses one prompt, capacity 128, and three generated SID components on the selected accelerator.

    Run from the source repository root in the installed CUDA or Ascend environment. Stop your own server before starting this separate engine so both processes do not compete for the device memory. Keep the model/tokenizer snapshot and artifact unchanged between preparation and inference.

    Choose the application interface¶

    Interface Application behavior Execution relationship
    GRLLM.beam_search_v1() A synchronous Python call returns final Beam outputs The engine still uses asynchronous scheduling internally.
    Async engine with GR adapters An event-loop application manages asynchronous submission, result delivery, and cleanup This does not inherently require HTTP; see the source pointers below.
    OpenAI-compatible HTTP service A client sends requests to a separately running server The server uses the asynchronous engine and GR frontend adaptation.

    Calling GRLLM directly does not make the application an AsyncLLM client. Conversely, asynchronous inference is not restricted to an HTTP deployment. The public beam_search_v1 name identifies the Beam protocol, separately from the native model runner. The example below keeps ModelRunner V1.

    Reuse the prepared configuration¶

    Use the same backend that you selected when generating the YAML. If it differs, regenerate the configuration through the preparation guide rather than changing only an environment variable.

    export BACKEND=cuda

    export BACKEND=npu

    Set the paths again in this shell. This uses the output directory from artifact and configuration preparation. If you reused the online guide instead, set WORKDIR to "$PWD/results/online-serving". Replace MODEL if needed. PROMPT refers to the short text file from the offline guide, not its length-padded token sequence:

    export MODEL="$PWD/models/OneRec-1.7B"
export WORKDIR="$PWD/results/data-preparation"
export GR_CONFIG="$WORKDIR/vllm_gr_config.yaml"
export PROMPT="$PWD/results/first-inference/prompt.txt"
export VLLM_USE_V2_MODEL_RUNNER=0
export VLLM_WORKER_MULTIPROC_METHOD=spawn
test -f "$MODEL/config.json"
test -f "$GR_CONFIG"
test -f "$PROMPT"

    Select an available device through your environment's allocation process. On NPU, retain the CANN and xllm-ops environments described by Ascend installation. Environment variables select inputs and visibility; they do not create the corresponding runtime or artifacts.

    The configuration loader is the public vllm_gr.config.load_gr_config() function. It returns a validated GRConfig and resolves relative artifact paths against the YAML's directory. GRLLM accepts that object, a canonical mapping, or a YAML path through vllm_gr_config. A mapping with relative paths does not automatically inherit the directory of some separately loaded YAML.

    Run a complete synchronous example¶

    Save the following program as python_beam.py under $WORKDIR. Using a real file and a __main__ guard lets spawned engine processes import the main module safely; do not replace the launch with Python executing from standard input when using the spawn process model.

    python_beam.py
    import json
import os
from pathlib import Path


def main():
    from vllm.inputs import tokens_input
    from vllm.platforms import current_platform
    from vllm_gr.config import BeamExecutionMode, load_gr_config, resolve_candidate_width
    from vllm_gr.entrypoints.gr import GRLLM
    from vllm_gr.sampling_params import BeamSearchParams

    backend = os.environ["BACKEND"]
    if backend not in {"cuda", "npu"}:
        raise ValueError("BACKEND must be cuda or npu")
    if str(current_platform.device_type) != backend:
        raise ValueError("BACKEND does not match the active accelerator runtime")
    model = Path(os.environ["MODEL"]).resolve()
    config = load_gr_config(os.environ["GR_CONFIG"])
    table = config.constraint_table
    if table is None or not table.enabled or table.backend.value != backend:
        raise ValueError("Use an enabled table configuration matching BACKEND")
    if config.beam_execution_mode is not BeamExecutionMode.V1:
        raise ValueError("The configuration must select beam.execution_mode=v1")
    if config.beam_max_width != 128 or config.beam_max_decode_steps < 3:
        raise ValueError("This example requires capacity 128 and at least 3 SID steps")
    if config.beam_worker_decision is not True:
        raise ValueError("Keep beam.worker_decision=true")
    if config.beam_graph_enabled != (backend == "cuda"):
        raise ValueError("Use the guide's CUDA graph or NPU eager configuration")
    candidate_width = resolve_candidate_width(config)
    if candidate_width != 128 or table.max_top_k < candidate_width:
        raise ValueError("Reuse the guide's candidate capacity of 128")

    params = BeamSearchParams(
        beam_width=128,
        max_tokens=5,
        temperature=0.0,
        ignore_eos=True,
        begin_token="<|sid_begin|>",
        end_token="<|sid_end|>",
        include_stop_str_in_output=True,
        length_penalty=1.0,
    )
    device_kwargs = {"block_size": 128} if backend == "npu" else {}
    with GRLLM(
        model=str(model),
        trust_remote_code=True,
        vllm_gr_config=config,
        async_scheduling=True,
        enable_prefix_caching=True,
        enable_chunked_prefill=False,
        max_model_len=512,
        max_num_batched_tokens=512,
        max_num_seqs=128,
        max_logprobs=candidate_width,
        gpu_memory_utilization=0.5,
        enforce_eager=backend == "npu",
        **device_kwargs,
    ) as llm:
        tokenizer = llm.get_tokenizer()
        text = Path(os.environ["PROMPT"]).read_text(encoding="utf-8")
        prompt_ids = tokenizer.encode(text, add_special_tokens=False)
        if not prompt_ids or len(prompt_ids) + params.max_tokens > 512:
            raise ValueError("Use a nonempty prompt fitting the full public token budget")
        print(f"input_tokens={len(prompt_ids)}; the API appends BEGIN")
        outputs = llm.beam_search_v1(
            [tokens_input(prompt_ids)], params, output_mode="compact"
        )
        for request_index, output in enumerate(outputs):
            print(f"request={request_index} returned_beams={len(output.sequences)}")
            for rank, sequence in enumerate(output.sequences[:5]):
                ids = list(sequence.token_ids)
                print(json.dumps({
                    "request": request_index,
                    "rank": rank,
                    "token_ids": ids,
                    "text": tokenizer.decode(ids, skip_special_tokens=False),
                    "cumulative_logprob": sequence.cumulative_logprob,
                    "finish_reason": sequence.finish_reason,
                    "stop_reason": sequence.stop_reason,
                }, ensure_ascii=False))


if __name__ == "__main__":
    main()

    Run the saved file from the same shell:

    python -u "$WORKDIR/python_beam.py"

    The YAML owns GR engine choices and artifact identity. Native engine options such as memory utilization and scheduling stay on the constructor. Request boundaries and the generation budget belong to BeamSearchParams. Do not add legacy catalog/Beam constructor overrides alongside the canonical configuration, or pass platform switches such as enable_npugraph_ex as arbitrary top-level GRLLM keywords. See Troubleshooting.

    This example encodes the complete file without padding or truncation. It conservatively reserves the full public five-position budget inside the 512-token limit. Do not append an extra BEGIN marker yourself: the API adds it before Prefill. Three SID components then require Prefill and two Decode forwards. The END marker is handled during completion/output conversion.

    The NPU example uses both beam.graph_enabled: false in its YAML and enforce_eager=True on the constructor. The CUDA example keeps the guide's graph-enabled configuration. Configured graph behavior is not evidence that all Prefill or Decode shapes actually replayed. Validate graph execution and numerical agreement separately before changing these settings.

    Read the output format explicitly¶

    compact is the default output mode; this example selects it explicitly. Its result records hold ordinary CPU token IDs and scores:

    Output Fields and contents
    One request result sequences plus one shared prompt_token_ids value containing the accepted original input.
    One compact candidate token_ids, cumulative_logprob, finish_reason, and stop_reason.
    Compact token_ids Generated suffix only, including configured BEGIN/END markers; the original prompt is excluded.
    Candidate text Decode its token IDs explicitly with the same tokenizer, as the script does.

    There can be fewer valid candidates than capacity 128. Printing five records does not reduce the search width. Scores are the search's cumulative log probabilities, not a normalized probability distribution over returned items. This functional example establishes no recommendation-quality or latency claim.

    The explicit alternative output_mode="full" returns native-style lazy Beam sequences. Their fields are tokens and cum_logprob, rather than compact token_ids and cumulative_logprob. Full tokens include the original prompt; reading full tokens/text can perform deferred CPU materialization. Do not change only the mode while keeping the compact-format field accesses above.

    Keep one engine alive for the requests your application owns instead of loading a model for every candidate. The context manager calls shutdown() on exit, including when the body raises an exception. It is separate from the per-call Beam session's release lifecycle. Stop using the engine after leaving the context; do not replace shutdown with termination of unrelated device processes.

    Async applications and HTTP¶

    This source snapshot does not export a GRAsyncLLM convenience class. It does contain an asynchronous Beam control flow, an async client adapter, and extensions to native AsyncLLM. These components can support an embedded asynchronous application without an HTTP transport. The engine-only adapter expects prepared Beam requests; it is not a drop-in await GRLLM.beam_search_v1() interface.

    Direct async integration must own input preparation, session submission, terminal result delivery, cancellation, release, and engine shutdown. This page does not turn those internal building blocks into an unverified public wrapper. For the supported request/response service workflow, follow Online serving; for a custom async frontend, begin with the lifecycle contract and the pinned implementations above.

    Use Python API reference for public fields and Advanced Beam features before changing the generation mode.
