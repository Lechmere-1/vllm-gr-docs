    Python API reference¶

    This page covers the public interfaces used by the first-release OpenOneRec/OneRec-1.7B guides. It is a curated reference for the pinned source snapshot, rather than an exhaustive mirror of every upstream vLLM class.

    GRLLM¶

    from vllm_gr import GRLLM

    GRLLM extends the installed vLLM LLM. Pass the local model and a canonical vllm_gr_config; supported native engine options pass through to vLLM. The complete Python example shows construction, request processing, and shutdown under a __main__ guard.

    Interface Behavior
    get_tokenizer() Return the tokenizer used by this engine.
    beam_search_v1(prompts, params, ..., output_mode="compact") Return one final Beam result per input prompt.
    generate(...) Ordinary LLM generation, separate from GR SID Beam selection.
    shutdown() Release the engine; the context manager calls it on exit.

    beam_search_v1() accepts token or text prompt structures. The tutorial uses vllm.inputs.tokens_input() after explicit tokenization. Optional call arguments include lora_request, use_tqdm, concurrency_limit, and trie_ids; availability remains subject to the chosen platform and engine contract. An argument in the signature does not establish every feature combination. In particular, lora_request is present in the signature, but current Beam V1 admission rejects LoRA requests.

    The retired beam_search() frontend is not an alternative to V1. Do not pass removed catalog_path or constraint_backend constructor arguments alongside canonical configuration.

    BeamSearchParams¶

    from vllm_gr.sampling_params import BeamSearchParams

params = BeamSearchParams(
    beam_width=128,
    max_tokens=5,
    temperature=0.0,
    ignore_eos=True,
    begin_token="<|sid_begin|>",
    end_token="<|sid_end|>",
    include_stop_str_in_output=True,
)

    This is a request object, not a standalone inference program. Capacity 128 must already exist in the engine. Two boundary positions leave three effective generated components. See Beam parameters and modes for dynamic widths, result limits, candidate schedules, and platform restrictions.

    Output records¶

    Mode Request result Candidate fields
    compact (default) sequences, shared prompt_token_ids token_ids, cumulative_logprob, finish_reason, stop_reason
    full Native-style lazy Beam output tokens, cum_logprob, and completion metadata

    Compact token IDs contain the generated suffix without repeating the original prompt. Boundary/stop inclusion follows the request's output options; the tutorial explicitly includes its markers. Decode with the same tokenizer. Full tokens include the prompt and may materialize lazily. Select an output mode explicitly when measuring API time or consuming results.

    The count is bounded by the requested return limit and legal candidates; capacity is not a promise of that many distinct returned items. An invalid request or a failed session is an error, not an empty successful accuracy test.

    Configuration helpers¶

    Function Result
    load_gr_config(path) Parse canonical YAML into GRConfig, resolving artifact paths against the file.
    gr_config_from_mapping(mapping) Validate a canonical mapping; artifact paths must be absolute without an explicit base directory.
    gr_config_to_mapping(config) Return canonical primitive values suitable for YAML/JSON.
    resolve_candidate_width(config) Resolve the configured candidate capacity.

    These are exported by vllm_gr.config. Parsing alone does not load a model or verify an artifact's contents. See Configuration reference.

    Async and HTTP boundaries¶

    There is no exported GRAsyncLLM convenience class in this snapshot. Native AsyncLLM and the GR async adapters can be embedded without HTTP, but direct integration must own the request/session lifecycle. Do not write await GRLLM.beam_search_v1(...) around the synchronous API.

    Use Python integration for the actual async entry points and Online serving for the supported HTTP walkthrough. HTTP Beam fields and response mapping are covered in Serving and batching.

    Experimental gRPC¶

    An optional gRPC entry point exists in the source package. A full user-facing gRPC walkthrough and its first-edition support matrix are reserved for later documentation. This edition's runnable examples use Python or HTTP; the transport contract records the underlying process/schema compatibility requirements.
