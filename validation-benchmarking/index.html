    Validation and benchmarking¶

    After Quickstart, check correctness before measuring performance. A successful request, numerical agreement, recommendation quality, graph replay, and latency are different kinds of evidence.

    This guide reuses the MODEL, CATALOG, and PROMPT paths from First offline inference. Run commands from the source repository root in the matching CUDA or Ascend environment, with an available device. Use an idle device and stop your other inference workloads before comparing timings.

    Decide what you are validating¶

    Check What to inspect
    Functional execution The request completes, outputs have the expected structure, and constrained candidates follow the catalog.
    Graph execution Actual capture/replay and fallback evidence for the intended Prefill and Decode shapes.
    Numerical agreement Candidate token sequences, ordering, and scores under otherwise matching conditions.
    Recommendation quality Recall or other task metrics on an identified dataset with ground truth and matching item mappings.
    Performance Repeated measurements with fixed inputs, an explicit timing boundary, and saved run conditions.

    Importing a package, collecting tests, or skipping unavailable tests does not establish inference correctness. Catalog-valid SIDs alone do not establish recommendation quality. A graph run does not by itself establish a speedup.

    Check numerical behavior¶

    For a baseline/candidate or NPU eager/graph comparison, hold model weights, tokenizer, catalog, prompt token IDs and lengths, dtype, batch size, Beam width, candidate count, generation budget, return limit, and cache policy constant. Record runner and graph settings as part of each case.

    Compare three things separately:

    1. The ordered list of returned token sequences.
    2. The set of candidates, to distinguish a ranking change from a changed search set.
    3. Scores for matching token sequences, rather than unrelated candidates at the same rank. Follow the owning test's numerical contract.

    Changing a dynamic Beam schedule or a candidate probability domain changes the search semantics. Such a comparison measures a quality/performance tradeoff, rather than numerical parity under an identical search.

    The development environment includes real-model system coverage. These commands load weights and run on the selected accelerator; they require pytest and the project's test dependencies as well as the inference runtime:

    VLLM_GR_TEST_MODEL="$MODEL" HF_HUB_OFFLINE=1 \
python -m pytest --run-slow -q -rs \
  tests/st/test_onerec_v1_scheduler_st.py

    VLLM_GR_TEST_MODEL="$MODEL" HF_HUB_OFFLINE=1 \
python -m pytest --run-slow -q -rs \
  tests/st/test_onerec_v1_npu_e2e.py

    Inspect the test summary and skip reasons. Passing these cases covers their configured workloads; validate the batch sizes, widths, input lengths, and model used by your deployment separately.

    NPU Prefill accuracy scope

    The bounded NPU graph subtest uses width 8 and exact Prefill buckets. It is not a width-128 business-quality benchmark. The source also documents an open padded-Prefill precision limitation; passing the exact-bucket case does not establish numerical agreement for arbitrary mixed-length padded inputs. See the recorded scope and reproducer.

    For task accuracy, use the established dataset and acceptance policy. The GPU five-task Recall gate and Video-100 gate used on NPU have different input and policy requirements. The GPU A100 calibration is not an absolute accuracy target for NPU. Read the preparation requirements before running a formal gate; do not change its thresholds to make a result pass.

    Measure offline API latency¶

    Use a fresh output directory for each experiment. The following also creates the parent directories used by tee and preserves failures in piped commands:

    export RUN_DIR="$PWD/results/beam-validation/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$RUN_DIR/json" "$RUN_DIR/logs" "$RUN_DIR/profile"
set -o pipefail
git rev-parse HEAD > "$RUN_DIR/source-revision.txt"
sha256sum "$CATALOG" "$PROMPT" > "$RUN_DIR/input-sha256.txt"

    Also record local source changes, the model snapshot, tokenizer/artifact identities, installed runtime versions, device, dtype, complete command, and graph environment settings. An unchanged path does not prove unchanged input contents. The benchmark JSON does not automatically record all of these details.

    Choose the command for the runtime being measured. For an NPU eager/graph comparison, run those two commands separately with the same prepared inputs:

    python -u examples/offline_inference/beam_search/offline_beam_search_v1.py \
  --model "$MODEL" --catalog "$CATALOG" --prompt "$PROMPT" \
  --constraint-backend cuda --execution graph \
  --batch-size 1 --beam-width 128 \
  --input-len 128 --generated-steps 3 --print-beams 5 \
  --warmup-runs 3 --repeat 20 \
  --output-json "$RUN_DIR/json/cuda-graph.json" \
  2>&1 | tee "$RUN_DIR/logs/cuda-graph.log"

    python -u examples/offline_inference/beam_search/offline_beam_search_v1.py \
  --model "$MODEL" --catalog "$CATALOG" --prompt "$PROMPT" \
  --constraint-backend npu --execution eager \
  --batch-size 1 --beam-width 128 \
  --input-len 128 --generated-steps 3 --print-beams 5 \
  --warmup-runs 3 --repeat 20 \
  --output-json "$RUN_DIR/json/npu-eager.json" \
  2>&1 | tee "$RUN_DIR/logs/npu-eager.log"

    python -u examples/offline_inference/beam_search/offline_beam_search_v1.py \
  --model "$MODEL" --catalog "$CATALOG" --prompt "$PROMPT" \
  --constraint-backend npu --execution graph \
  --batch-size 1 --beam-width 128 \
  --input-len 128 --generated-steps 3 --print-beams 5 \
  --warmup-runs 3 --repeat 20 \
  --output-json "$RUN_DIR/json/npu-graph.json" \
  2>&1 | tee "$RUN_DIR/logs/npu-graph.log"

    The CUDA command explicitly labels the report as graph; --execution still only controls the NPU runtime. It is not a CUDA eager/graph toggle.

    What the timer includes¶

    The script runs three untimed warmup batches, then measures 20 complete beam_search_v1(..., output_mode="full") calls until output objects return. For this three-component example, each call includes Prefill and two Decode forwards, together with the API work needed to return the results.

    Engine startup, artifact compilation, warmup, pre-call prompt preparation, and post-call result inspection/printing are outside the timing boundary. Prefix Cache remains enabled, but independent salts per row and run force cold Prefill; this is not a prefix-cache-hit benchmark.

    This is batch API latency. It is neither device-kernel-only time nor HTTP latency. For larger batches, dividing batch P50 by batch size gives an amortized cost, not the latency experienced by each request.

    Read the benchmark JSON¶

    The JSON file contains the report directly. Standard output wraps the same report under beam_benchmark. For example, after the NPU graph run:

    python - "$RUN_DIR/json/npu-graph.json" <<'PY'
import json
import sys
from pathlib import Path

report = json.loads(Path(sys.argv[1]).read_text(encoding="utf-8"))
print(report["timing_scope"])
print("batch P50 (ms):", report["batch_latency_ms"]["p50"])
print("batch P95 (ms):", report["batch_latency_ms"]["p95"])
print("requests/s:", report["requests_per_second"])
print("returned beams/s:", report["returned_beams_per_second"])
PY
    Field Meaning
    batch_latency_ms Mean, P50, P95, minimum, and maximum batch API latency, in milliseconds.
    requests_per_second Timed request count divided by total timed seconds.
    returned_beams_per_second Actual returned candidate count divided by total timed seconds.
    runs[].returned_beams Actual total returned candidates across the whole batch in that run.
    npu_beam_graph Capture, replay, and fallback diagnostics for NPU graph runs.

    The benchmark file does not serialize all candidate token IDs and scores. Only the final batch's leading results are printed, limited by --print-beams. Use a dedicated correctness run to capture complete results for numerical comparison; the timing JSON alone is not precision evidence.

    Twenty samples form a short local measurement. Repeat controlled experiments and inspect run-to-run variation before claiming a regression or improvement. Changing the search width or return limit also changes the workload, so record it when comparing throughput.

    Collect a separate profile¶

    Use the same inputs and workload, but collect traces in a separate process:

    python -u examples/offline_inference/beam_search/offline_beam_search_v1.py \
  --model "$MODEL" --catalog "$CATALOG" --prompt "$PROMPT" \
  --constraint-backend cuda --execution graph \
  --batch-size 1 --beam-width 128 \
  --input-len 128 --generated-steps 3 --print-beams 5 \
  --profile-dir "$RUN_DIR/profile/cuda-graph" \
  --profile-warmup-runs 1 --profile-runs 5 \
  2>&1 | tee "$RUN_DIR/logs/cuda-graph-profile.log"

    python -u examples/offline_inference/beam_search/offline_beam_search_v1.py \
  --model "$MODEL" --catalog "$CATALOG" --prompt "$PROMPT" \
  --constraint-backend npu --execution graph \
  --batch-size 1 --beam-width 128 \
  --input-len 128 --generated-steps 3 --print-beams 5 \
  --profile-dir "$RUN_DIR/profile/npu-graph" \
  --profile-warmup-runs 1 --profile-runs 5 \
  2>&1 | tee "$RUN_DIR/logs/npu-graph-profile.log"

    The profiler starts after engine initialization and one unprofiled warmup, then collects five complete batches before output printing. It records the Worker side with stack, shape, and memory recording disabled. Inspect the supplied directory and its worker/rank subdirectories for traces.

    Do not combine --repeat with --profile-dir. In direct Beam mode, --output-json requires --repeat, so leave it out of profiling commands too. Do not layer this collection with msprof or use profiled samples as the unprofiled latency result.

    Profiles help locate TensorMove, TopK, attention, and other operator costs. Fewer operators or lower copy time is a hypothesis for an improvement; confirm the effect with separate API latency measurements.

    Verify graph evidence and record the conclusion¶

    For NPU graph runs, inspect captured_shapes, full_dispatches, fallbacks, and fallback_reasons under npu_beam_graph. Counters include warmup as well as collected or timed runs, so do not expect only the measured Decode count. A one-step run ends in Prefill without Decode replay. A fallback does not necessarily mean a purely eager forward.

    Keep the evidence separate in your report: functional result, numerical or quality comparison, observed graph shapes, timing scope, measured latency distribution, and relevant profiles. Use the same saved conditions when checking a code change in a fresh process.

    Formal CI acceptance has additional input and policy checks. See the validation levels and benchmark acceptance guide before using the CI-oriented runners. Local demo measurements do not replace those gates.

    If a run fails or graph execution differs from the intended mode, start with Troubleshooting and keep the first underlying error with your validation record.
