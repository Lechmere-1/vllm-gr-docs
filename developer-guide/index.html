    Developer guide¶

    vLLM-GR extends an installed vLLM runtime. Begin with the selected platform's CUDA installation or Ascend installation, then use this guide to find the owning code before changing behavior. The main model walkthrough uses OpenOneRec/OneRec-1.7B; model weights are separate inputs.

    Prepare the actual development runtime¶

    Run commands from the inference repository root, in an environment prepared for the device. On Ascend, retain the vendor runtime and loaded CANN/xllm-ops environment; installing the GR package does not provision those dependencies.

    VLLM_GR_TARGET_DEVICE=cuda pip install -e ".[dev]"
vllm-gr check-env

    VLLM_GR_TARGET_DEVICE=npu pip install -e ".[dev]" --no-build-isolation
vllm-gr check-env --npu

    Confirm which checkout the interpreter imports before runtime validation:

    python --version
python -c 'import vllm_gr; print(vllm_gr.__file__)'
git rev-parse HEAD

    A sibling source directory is a reference, not proof of the imported package. Keep version constraints in pyproject.toml, setup.py, requirements/, and vllm_gr/_env_check.py aligned. check-env does not run a model or establish that an accelerator has enough free memory. Follow testing and CI for the checks appropriate to the change.

    Find the owner and contract¶

    Change Code owner Read first
    Package initialization and runtime patches vllm_gr/plugin.py, patch.py, _env_check.py Patch inventory
    Configuration and offline Python API vllm_gr/config/, entrypoints/gr.py Python integration, parameters
    HTTP/gRPC, admission, scheduling, cleanup vllm_gr/entrypoints/, v1/engine/ Batch lifecycle contract
    Beam state, selection, parent lineage vllm_gr/v1/beam/ Decision contract, Beam explanation
    Worker, Attention, and graphs vllm_gr/v1/worker/, v1/attention/backends/, ops/ Development map, Prefill graph contract
    Catalog artifacts and candidate scoring vllm_gr/constraints/, tools/build_constraint_table.py Data and constraints, scoring implementation
    Platform registration and activation vllm_gr/platforms/ Platform backend contract

    The frontend submits a logical batch and waits for the terminal result. EngineCore owns session progress, native scheduling owns prompt accounting and paged KV blocks, and Workers own device state. Preserve those ownership boundaries, including failure, cancellation, retirement, and resource release. Increasing storage capacity does not grant additional concurrent owners.

    Preserve platform and patch boundaries¶

    Top-level import vllm_gr stays lightweight. Runtime initialization belongs to plugin.initialize_runtime() and the general-plugin entry point. Main, EngineCore, and Worker processes initialize independently; a frontend-only check does not prove that a spawned Worker installed its hooks.

    Provider registration must avoid hardware imports. Activation, environment checking, runtime compatibility patches, Worker hooks, and Attention dispatch are distinct boundaries. Use the canonical device names cuda and npu. Read the platform contract before changing fallback or import behavior.

    When changing patch targets, ownership, activation, or removal, update both docs/runtime_patch_inventory.md and docs/patch_inventory.yaml, together with the relevant contract coverage. Do not hand-edit generated gRPC bindings or vllm_gr/_version.py; use the owning generation/build procedure. Beam protocol V1 and ModelRunner V1/V2 are separate selections. Preserve ordinary non-GR inference when modifying a shared patch or transport.

    Prepare a reviewable contribution¶

    1. Read the checkout's AGENTS.md, Contributing, and owning contract.
    2. Make a focused branch and keep unrelated edits out of the change.
    3. Reproduce a bug before its fix when practical, then verify the same case.
    4. Update affected public examples and contracts, and select meaningful checks.
    5. Describe the problem, resulting behavior, exact validation, and remaining gaps.

    Use the inference repository's PR template. Keep passed, failed, skipped, and unrun coverage separate. Functional output, graph replay, recommendation accuracy, and latency are different forms of evidence. For device results, retain the imported revision, runtime/device/model identity, configuration, command, and artifact paths.

    Commit with your correct Git identity and a DCO sign-off, for example git commit -s. The configured commit-message hook also adds a Signed-off-by line when needed; inspect the final commit rather than assuming the hook ran. Do not claim authorship or validation performed by someone else.

    Keep inference development separate from website publication¶

    The rules above describe contributions to the inference repository. A separate documentation publication repository may hold generated website output and use different build/deployment checks. Publishing a site does not grant runtime repository write access or make the documentation source publicly editable. Use the actual source repository and its permissions when proposing edits; do not edit generated HTML as a substitute for changing the maintained source.
