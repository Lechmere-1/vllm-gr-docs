    Models and capabilities¶

    Choose a model and an inference path together. A checkpoint that generates text does not automatically contain recommendation SID tokens, a business catalog, or trained SID embeddings.

    This guide describes the source snapshot used by this documentation preview, c4966f18. A supported code path is not a claim that every checkpoint, device, batch shape, or feature combination has passed hardware validation.

    Choose an entry point¶

    Your goal Model and data Start here
    Run the standard recommendation example OneRec weights and tokenizer with the matching SID vocabulary; a compatible triples catalog First offline inference, then Online serving
    Generate ordinary text with public Pangu weights The public openPangu Embedded 1B checkpoint and its original tokenizer Pangu text inference example
    Exercise SID Beam execution using public Pangu assets A separately converted SID checkpoint and a matching synthetic catalog Pangu SID preparation workflow
    Search the full model vocabulary without a catalog A supported text decoder and an explicit unconstrained Beam configuration NPU unconstrained Beam guide; CUDA callers use the same public Beam API with the CUDA runtime
    Generate a thinking continuation before SID selection A checkpoint with the required thinking tokens and behavior, plus a compatible SID catalog Thinking and SID Beam example

    The ordinary Pangu example uses GRLLM.generate(), which follows the standard vLLM generation path. The recommendation examples use GRLLM.beam_search_v1(). HTTP recommendation requests select Beam explicitly with use_beam_search: true; starting a server alone does not select that path.

    The offline Python API and the HTTP service are separate frontends to the engine. An asynchronous engine does not require an HTTP server, and an offline GRLLM call can still use asynchronous scheduling internally. See the Beam execution contract for request ownership and lifecycle.

    Know which component owns what¶

    Component Role What it does not supply
    Model configuration and weights Define the network, vocabulary dimensions, embeddings, and output projection used for inference A business item catalog or ground-truth evaluation dataset
    Tokenizer files Map text and SID symbols to token IDs and decode IDs back to text Trained vectors for newly added tokens
    Catalog or triples document Define which A/B/C SID combinations are legal recommendation candidates Learned probabilities or model training
    Compiled Constraint Table Turn catalog relations into an artifact for the selected backend, tied to its tokenizer identity A replacement for the model weights or tokenizer
    SID-to-item mapping Map complete generated SIDs to business item identifiers A guarantee that a randomly initialized SID model recommends useful items

    Tokenizer assets are normally stored beside the weights in a model directory, but tokenization is outside the model's tensor forward computation. The token embedding and output projection are model tensors. Adding tokenizer entries without corresponding weight rows is not sufficient to extend a checkpoint.

    A catalog can constrain a model to emit legal symbols even when the model has not learned useful preferences over those symbols. Legal output and useful recommendations therefore need different validation.

    Use the same immutable local model/tokenizer snapshot when compiling the Constraint Table and running inference. A path name is not an identity check. The artifact and tokenizer digests in the canonical configuration identify the compiled inputs; changing the tokenizer or catalog requires rebuilding them. See Beam parameters and modes for the configuration fields and boundary-token budget.

    Start with OneRec¶

    The main walkthrough uses OpenOneRec/OneRec-1.7B, its tokenizer, the tracked video triples fixture, and a short prompt. It downloads weights separately from the framework and runs one request with capacity 128 and three generated SID components. Follow First offline inference without combining advanced options on the initial run.

    The constrained example generates A, B, and C components. Its configured BEGIN and END positions are additional public-output positions, so max_tokens=5 represents three generated components. A one- or two-component run produces a valid catalog prefix; it is not a complete three-component item identifier.

    The standalone example accepts a triples JSON document and compiles a temporary artifact. The online service instead loads a persistent artifact and canonical configuration. These inputs are not interchangeable command-line arguments.

    For business use, replace the fixture with the catalog and SID-to-item mapping that belong to your model and task. Do not treat the example prompt, candidate legality, or one successful request as a Recall measurement. Use Validation and benchmarking for separate functional, numerical, recommendation-quality, and performance checks.

    Distinguish the two public Pangu workflows¶

    Ordinary text generation¶

    The repository provides an offline text-generation example and HTTP serving instructions for public openPangu Embedded 1B weights. This route does not require adding SID symbols or creating a recommendation catalog.

    The Pangu compatibility layer preserves the checkpoint's declared tied embedding behavior. The public checkpoint can contain a zero-filled lm_head.weight placeholder; treating that placeholder as an independent output head would produce incorrect all-zero logits. This compatibility fix does not create a new Pangu architecture or train a recommendation model.

    Use the Pangu-specific runtime settings from the example guide, including the slow tokenizer and its cache settings. Its NPU path selects KV block size 128. The ordinary text-generation settings are not a replacement for the canonical Beam configuration in the recommendation guides.

    SID execution with a converted checkpoint¶

    At this source snapshot, the project's SID-extended Pangu checkpoint is not publicly available. The preparation tool makes execution smoke tests possible from public openpangu/openPangu-Embedded-1B-V1.1 assets.

    Preparation reads a local public snapshot and writes a separate output directory. It refuses an existing destination and validates the result on CPU before publishing it. It expects the public Pangu architecture, original vocabulary size, tied embedding layout, and safetensors weights; it is not a generic converter for arbitrary Pangu checkpoints.

    The conversion performs these operations:

    1. Preserve existing token IDs and original tokenizer entries, then add 8192 symbols in each of the A, B, and C SID families plus BEGIN and END markers.
    2. Expand the embedding tensor and initialize new SID and padding rows randomly using a fixed seed. Preserve the original embedding prefix and other model tensors.
    3. Materialize the tied output-head weights from the expanded embedding instead of retaining the public checkpoint's zero placeholder, and update vocabulary metadata.
    4. Write token-layout, tensor-inventory, and conversion-manifest reports with checksums and CPU validation results.

    This changes tokenizer assets, vocabulary metadata, and embedding/output-head storage. It is not accurate to call the converted checkpoint byte-for-byte unchanged. It also does not train the new rows: their initialization supplies executable tensors, not learned recommendation knowledge.

    The tool records a caller-declared source revision and hashes the local source files. Its manifest explicitly reports revision_verified: false; the revision label alone is not proof that local files came from that remote commit.

    The documented smoke workflow builds a small synthetic catalog and uses the existing constrained Beam example. The catalog fixes legal A/B/C combinations, so successful output can look like valid SIDs despite random new weights. This establishes neither business accuracy nor a speedup. Preparation does not require an accelerator; inference still requires the matching CUDA or Ascend runtime. The guide provides commands for both backends, rather than claiming identical results on every GPU and NPU.

    Separate the Beam protocol from the model runner¶

    beam.execution_mode: v1 and beam_search_v1() name the GR Beam protocol. They do not mean that every model forward must use native ModelRunner V1.

    The runtime selection policy defaults to ModelRunner V1 before vLLM initialization. An explicit VLLM_USE_V2_MODEL_RUNNER=1 is preserved as an experimental opt-in. The documented V2 adaptation targets CUDA; its runner guide records the workload, storage, capture, and lifecycle scope. Do not infer support for every V1 feature combination from that opt-in.

    The NPU guides use ModelRunner V1. In particular, the NPU unconstrained adapter explicitly rejects ModelRunner V2. Switching runners does not bypass model, generation-budget, artifact, or parallelism validation.

    Check capabilities by execution path¶

    The table below summarizes the default ModelRunner V1 Beam paths in this snapshot. It does not turn separate capabilities into a promise that all of them can be combined.

    Capability CUDA Beam V1 path Ascend NPU Beam V1 path
    Three-component catalog-constrained generation Canonical CUDA table Canonical NPU table and required NPU operators
    Full-vocabulary Beam without catalog membership Explicit unconstrained configuration Explicit unconstrained configuration; effective budget remains 1 through 3
    Dynamic retained widths and final result limit Python and HTTP interfaces Python, HTTP, and the standalone demo; keep scalar candidate width unset for changing widths
    Independent per-parent candidate schedules per_parent_beam_widths, subject to request and engine limits Not supported in this snapshot
    Multiple independent catalog Tries in one artifact Supported through per-request Trie selectors Multi-Trie artifacts and nonzero Trie selectors are rejected
    Catalog-free A/B/C stage domains Not the NPU stage-domain feature Opt-in beam.sid_stage_vocab, only with unconstrained generation
    Decode graph execution CUDA capture and replay policy Exact logical batch and Decode input-width capture, with separate fallback behavior

    Constrained generation remains limited by the three-level table; increasing beam.max_decode_steps does not deepen the catalog. The current NPU unconstrained adapter also limits generation to 1 through 3 tokens. Ordinary LLM text generation is a different path and does not remove these Beam limits.

    The multi-Trie contract uses one model vocabulary and tokenizer for all Tries. A request selector chooses a catalog root, not another model or another checkpoint. CPU table compilation/reference support does not establish a production CPU Beam inference engine.

    In NPU catalog-free SID stage mode, selecting A/B/C families is not catalog membership checking. Stage-local probability normalization differs from full-vocabulary normalization and can change scores and cross-parent rankings. Compare implementations under the same probability domain. See the unconstrained scoring contract before enabling this mode.

    For graph shapes and width rules, follow Beam parameters and modes. A graph-enabled setting is not evidence of actual replay, and replay is not a guarantee of numerical agreement for arbitrary padded Prefill inputs.

    Treat thinking as a separate model capability¶

    The offline demo has two distinct optional routes: --enable-thinking performs ordinary full-vocabulary generation, while --cot generates a thinking continuation and then runs constrained SID Beam Search. They are mutually exclusive. Neither flag teaches reasoning to weights that do not support it.

    The combined path requires dedicated <think> and </think> tokenizer tokens, a matching SID vocabulary/catalog, and enough context for both phases. It hands off token IDs and performs fresh Beam Prefill; it does not reuse thinking KV across phases. Its thinking budget does not extend the SID table's depth.

    The source workflow documents the NPU setup and explicitly does not include CUDA hardware validation of the combined example. The shared script accepts both backends, which is different from proving equivalent quality, timing, or graph coverage on both. Qualify the chosen model, frontend, runner, and platform through validation.
