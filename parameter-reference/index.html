    Beam parameters and modes¶

    Use this reference after First offline inference or Online serving. Start with one prompt, capacity 128, three SID components, and the matching platform configuration, then change one setting at a time.

    This page describes the vLLM-GR 0.30 source used by these guides. A field being accepted by the configuration parser does not mean every accelerator supports every combination. Device-specific limits are called out below.

    Capacity, candidates, retained width, and results¶

    These four quantities serve different purposes:

    Quantity Meaning
    Capacity W Engine storage and request capacity, configured by beam.max_width. Request beam_width must equal it.
    Candidates K How many token candidates each parent Beam can contribute before global selection.
    Retained width w_t How many winning prefixes survive after generated component t. A dynamic schedule sets one value per component.
    Result limit R Maximum final sequences returned to the caller. It does not reduce earlier search widths.

    At each stage, candidate children compete globally to fill the retained width. One parent can contribute several winners, and another can contribute none. Limiting candidates per parent does not guarantee that every parent survives. The selected children carry their parent indices into KV inheritance and reordering, so each next-step prefix reads the history of its selected parent.

    In the fixed-width default, w_t = W and the candidate count follows that width. For a dynamic schedule with candidate width left unset, candidate selection follows the current stage's retained width. An explicitly configured scalar candidate_width fixes the candidate count instead, unless a supported per-stage per-parent schedule overrides it. Check the platform limits below.

    Reducing result_width limits the final returned set. Reducing --print-beams only prints fewer records in the offline demo. Neither option is a substitute for narrowing the search schedule.

    Where to set each parameter¶

    Engine startup configuration¶

    Change these in the YAML passed to --vllm-gr-config, or in the Python vllm_gr_config mapping, before constructing the engine:

    Setting Rule
    beam.execution_mode Use v1 for beam_search_v1().
    beam.max_width Match every request's beam_width or HTTP n. The guides use 128.
    beam.max_decode_steps Must cover the effective generation budget, including the first component produced by Prefill.
    beam.worker_decision Keep true for the V1 path.
    constraint_table.candidate_width Optional engine-wide scalar K; leave unset for the NPU examples here.
    constraint_table.max_top_k Candidate storage limit; must cover the candidate counts required by the chosen execution path.
    beam.graph_enabled Enable the Beam Decode graph path; this is separate from Prefill graph controls.
    beam.graph_batch_size Exact NPU logical batch size for Beam Decode graph replay.
    beam.graph_widths Additional exact NPU Decode input widths to capture.
    beam.online_batch_sizes Policy for supported HTTP prompt-list batch sizes, not the request's Beam width. The online guide starts with [1].

    The artifact path, artifact digest, tokenizer digest, and device backend must describe the same model/tokenizer and constraint table. Do not mix canonical configuration with legacy catalog or Beam CLI overrides.

    Per-request parameters¶

    Python uses vllm_gr.sampling_params.BeamSearchParams. HTTP uses the fields below with use_beam_search: true:

    Python field HTTP field Rule
    beam_width n Must equal engine beam.max_width, even with a dynamic schedule.
    max_tokens max_tokens Public generation budget, including configured begin/end positions.
    begin_token, end_token Inside vllm_xargs Use boundary tokens present in the checkpoint's tokenizer.
    dynamic_beam_widths vllm_xargs.dynamic_beam_widths One retained width per effective generation step, each between 1 and capacity.
    result_width vllm_xargs.result_width Between 1 and the final retained width; defaults to that final width.
    per_parent_beam_widths vllm_xargs.per_parent_beam_widths Per-stage candidate counts; currently CUDA-only.
    ignore_eos ignore_eos V1 uses a fixed budget. Set true in Python; the online entry supplies true itself.
    length_penalty length_penalty Final ranking control, separate from search capacity and candidate count.

    For the canonical Constraint Table path, leave catalog_strategy unset. The Worker-side table controls candidate validity.

    Offline demo arguments¶

    The standalone offline_beam_search_v1.py builds the engine configuration as well as the request. Its argument names are not identical to the Python API:

    CLI argument Effect
    --beam-width Sets both engine capacity and request width.
    --generated-steps Effective SID steps, with choices 1, 2, or 3.
    --candidate-width Sets the engine's scalar candidate count; it is not the thinking sampler's --top-k.
    --dynamic-beam-widths Per-stage retained widths; this demo currently exposes this option only for NPU.
    --result-width Final return limit; this demo currently exposes this option only for NPU.
    --execution eager/graph NPU execution selection; it does not switch CUDA to eager mode.
    --input-len Prepares a fixed-length prompt for direct SID Beam, including the appended begin token.
    --print-beams Display limit for the returned records.

    In direct SID Beam mode, the script sets public max_tokens to --generated-steps + 2 and Beam temperature to 0.0. Its --max-tokens, --temperature, --top-p, and --top-k arguments control thinking generation, not direct SID Beam selection. There is no demo CLI flag for per_parent_beam_widths; use the Python or HTTP interface on CUDA.

    Count generation steps correctly¶

    The effective generation budget is:

    N = max_tokens - configured_begin_position - configured_end_position

    Each configured boundary reserves one position. With both OneRec markers, max_tokens=5 means N=3: Prefill selects A, then two Decode forwards select B and C. A surviving fixed-length result receives its configured end marker during output conversion; the marker is not another sampled Decode step.

    The constraint_table_v1 path supports effective budgets 1 through 3. Use three components for the complete A/B/C SID example. A one-step run finishes in Prefill and should not be expected to report a Decode graph replay.

    Increasing beam.max_decode_steps alone does not extend the constraint table's depth. The current NPU full-vocabulary Beam path also supports only 1 through 3 steps; do not infer longer-step support from ordinary LLM generation.

    Dynamic narrowing and widening¶

    Keep engine and request capacity at 128. Both of these schedules fit within that capacity:

    Schedule After Prefill: A After Decode 1: B After Decode 2: C Example return limit
    Narrowing 128 64 32 16
    Widening 32 64 128 16

    Each value is a retained prefix count, not a new engine capacity. Expanding a later stage creates more children of the surviving parents; it cannot recover prefixes already pruned at an earlier stage. Different schedules can change rankings and recommendation quality.

    The examples below reuse the exported MODEL, CATALOG, and PROMPT paths from First offline inference. They leave scalar candidate_width unset and use the NPU demo's graph configuration:

    python -u examples/offline_inference/beam_search/offline_beam_search_v1.py \
  --model "$MODEL" --catalog "$CATALOG" --prompt "$PROMPT" \
  --constraint-backend npu --execution graph \
  --batch-size 1 --beam-width 128 \
  --input-len 128 --generated-steps 3 \
  --dynamic-beam-widths 128,64,32 --result-width 16 \
  --print-beams 5

    python -u examples/offline_inference/beam_search/offline_beam_search_v1.py \
  --model "$MODEL" --catalog "$CATALOG" --prompt "$PROMPT" \
  --constraint-backend npu --execution graph \
  --batch-size 1 --beam-width 128 \
  --input-len 128 --generated-steps 3 \
  --dynamic-beam-widths 32,64,128 --result-width 16 \
  --print-beams 5

    Python and HTTP support retained-width schedules on CUDA as well as NPU. The demo's NPU-only CLI restriction is not a CUDA engine limitation.

    Match NPU graph shapes to Decode inputs¶

    A three-component schedule has only two Decode input widths:

    Retained schedule Decode input widths Suggested beam.graph_widths
    [128, 64, 32] 128, then 64 [64, 128]
    [32, 64, 128] 32, then 64 [32, 64]

    The last retained width has no following model forward. NPU graph matching uses logical batch size and input width together, so a B=1 capture does not establish B=4 replay. The maximum-capacity width is included implicitly; the configuration allows at most eight distinct width captures including it. More captures increase startup and device-memory requirements.

    The offline demo derives its graph widths from the schedule. When editing an online configuration yourself, set the matching graph_batch_size and graph_widths before restarting. For NPU graph execution, also set graph_enabled: true and remove --enforce-eager, as shown in Online serving.

    A graph fallback counter means the Beam FULL graph was not used; it does not exclusively count eager forwards. Prefill capture has separate controls and shape restrictions. Use execution diagnostics or profiles to establish what actually replayed, and validate numerical behavior separately.

    Candidate-width and platform limits¶

    On CUDA, per_parent_beam_widths sets one candidate count per effective step. The first must equal the first retained width. At each later step, the retained width cannot exceed the previous retained width times the per-parent candidate count. These are candidate limits, not a guarantee of one winner per parent.

    The configuration schema has a global capacity ceiling of 1024 and candidate ceiling of 256. Capacity above 256 requires an explicitly configured candidate width at or below 256. These numeric ceilings are not a claim that every NPU shape or CUDA workload has been validated on hardware.

    Feature CUDA V1 NPU V1 in this source version
    Three-component catalog-constrained Beam Supported Supported
    Dynamic retained widths and final result limit Python/HTTP interfaces Python/HTTP and the standalone demo
    Independent scalar candidate count Supported within the configured limits Keep unset; the NPU path requires candidate and retained widths to agree.
    Per-stage per_parent_beam_widths Supported within request and engine limits Not supported
    Multi-Trie request selection Separate CUDA configuration Not supported

    An explicit scalar candidate_width must fit the candidate storage and max_logprobs budget. For a dynamic retained-width schedule without a per-stage candidate override, it must be at least every retained width. On NPU, leave it unset for changing retained widths; setting a fixed candidate count is not a way to enable independent candidate selection there.

    Choose the generation mode¶

    Mode What it generates How to select it
    Catalog-constrained SID Beam Prefixes that follow the supplied catalog table Use the enabled canonical Constraint Table in the offline/online guides.
    Full-vocabulary Beam Model-vocabulary tokens, without catalog membership guarantees Use the public Python Beam API with constrained_generation: false and a disabled table.
    Catalog-free SID stage domains A, then B, then C token families, without validating the combined item On NPU, add beam.sid_stage_vocab: true to the unconstrained configuration.
    Thinking only Ordinary LLM generation, without a SID Beam phase The demo's --enable-thinking mode.
    Thinking followed by SID Beam A thinking continuation, then constrained SID search The demo's --cot mode and a compatible model/tokenizer/catalog.

    --cot and --enable-thinking are mutually exclusive. Their thinking budget and sampler settings are separate from the SID Beam budget. A model must support the intended thinking behavior; selecting a mode does not add that capability to arbitrary weights.

    The current NPU unconstrained path uses ModelRunner V1, FP16/BF16, asynchronous scheduling, and single-device parallelism. The SID stage domain is limited to three components. See the NPU unconstrained Beam guide for its complete configuration and scoring contract.
